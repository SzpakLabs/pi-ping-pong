# PPP permission-friction research

**Scope:** read-only audit requested from the PPP source repository. No run was launched or changed; no code, installed extension, safeguards, global settings, or Freya contract was modified. The Freya run was inspected selectively (TASK, evaluator, final report/follow-up, safe fixture and identity evidence, bridge event summaries and terminal status). No full transcript or credential-bearing material was copied.

## B. Case causality (verified / inference / unknown)

**Verified from local artifacts:**

1. The task named one exact local runtime/theme and required stopping if identity could not be confirmed; it prohibited runtime lifecycle changes, remote writes, source/Admin edits, orders/payments and inventory changes. It explicitly allowed isolated test-cart use, subject to availability.
2. Cycle-1 durable status says worker reported HTTP401 and could not independently verify identity, therefore the reviewer used `waiting_human`. The event/status summary says the evidence did not yet include a sanitized raw response. The task had required exact identity verification before testing. This was initially a legitimate safety stop, not proof that every later check required the owner.
3. Later `identity.json` records HTTP200 and rendered development-theme ID/role matching the requested target. That is fresh later evidence; it does not validate the earlier 401 or authorize a different target. A bounded fallback/recheck could have restored this identity-dependent work without asking the owner again if it stayed within task permissions.
4. `fixture-availability-cycle6.json` shows HTTP 200 product resources but all five requested cart variants unavailable. `REPORT.md` states no cart mutation was attempted and cart remains NOT TESTED. Inventory alteration was not authorized. Cart unavailability was real, but only blocks cart criteria.
5. The run recorded owner approval of Editor/settings and shown appearance at cycle 8. Cycle-9 review summary explicitly says not to request it again. Final report retains that scoped approval and does not claim independent screenshot inspection.
6. Final artifact is PARTIAL / stopped at 10/10, eval exit 1; `bridge-status.json` is stopped. The report records navigation as open/unknown, cart not tested, and verified collection/filter checks. It does not claim overall QA/LIVE pass.
7. Installed bridge equals canonical `scripts/bridge.py` at SHA-256 `061815…2ff8`. Installed receiver and docs are older/different: installed `pi-reviewed.ts` lacks canonical named-task and Git-env changes; installed SKILL/reference docs lack current edits. This drift is unrelated to the recorded bridge decisions but demonstrates installed parity cannot be assumed. The currently canonical preparation prompt asks to confirm project root/allowed paths; a current prompt’s exact output was not captured in the old run, so it cannot be asserted as causal.

**Strong inference:**

- The observed friction arose from interaction of a strict all-criteria evaluator, checkpoint-wide human-resolution invariant, coarse `needs_human` status, and reviewer/task instructions, rather than a single bridge defect. The protocol correctly blocked proceeding through a declared human gate, but represented a locally scoped gate as a whole-cycle hold.
- After the initial 401, later matching identity evidence appears to have made additional read-only work possible. Whether bridge/reviewer actually delayed browser fallback, and why, is not proven solely by durable state/events; the task contract already required stopping on unconfirmed identity.
- “Unavailable fixtures” and “navigation harness/evidence” becoming recurring revise work is consistent with evaluator output demanding all IDs pass and artifacts meet rigid schemas. The evaluator was correctly refusing false PASS; lack of partial criteria/status support likely encouraged repeated attempts to turn unavailable/unknown checks into passing evidence.
- Run exhaustion at cycle 10 was correct. Additional revise cycles or extending budget would not be justified by failures alone.

**Unknown / not established:**

- Exact HTTP401 response source, duration, cause, and whether browser fallback was technically available at that moment. No copied raw/private logs were used.
- Every individual prompt/review text and whether it asked for “fixtures” or repeated approvals; full transcript review was deliberately out of scope. Event summaries establish selected decisions only.
- Whether the Bouquets H1/URL mismatch is a bug or intended navigation behavior; the final follow-up says cause unknown.
- Whether Editor screenshot attachments match the owner’s confirmation; final report explicitly says the worker could not inspect them.
- No actual fresh source checkout or global extension implementation was run in this audit. No runtime integration/live tests were conducted.

## C. Prioritized patch plan (proposal only)

1. **Task/preparation prompts:** distinguish read permission from write permission; reuse permissions and choices already stated; ask only for a missing/conflicting decision; make blocked scope explicit and permit independent authorized work. Avoid requiring blanket path confirmation. Do not infer implementation permission from a read-only audit.
2. **Reviewer prompt:** add a compact criterion dependency map: which action is blocked, what remains authorized, whether existing approval covers the exact scope/state, and which user question (if any) must be bundled. Classify auth/access/approval/choice separately from HTTP errors, selectors, fixtures, schema, and evidence gaps. Continue/revise technical issues inside budget without weakening checks.
3. **Lifecycle/API (design first, compatibility-preserving):** current `needs_human` + `human_resolved` is checkpoint-wide; do not weaken it casually. Define versioned blocker records bound to criterion/action/state, separate independent progress, authentic resolution provenance, and final full-acceptance status. Introduce explicit non-success partial/blocked/stopped result if required, distinct from Goal completion. Retain current decision CLI/config compatibility via adapter/migration; no claiming feature exists before implementation.
4. **Evaluator contract:** per-criterion `pass/fail/blocked/not_tested`, required-vs-optional/dependency metadata, errors separate from missing data and human approval. Unknown is never pass; “report complete” cannot mean “product task passed.” Fresh eval, independent reviewer, evidence hashes and final requirements remain mandatory.
5. **Budget/termination:** maintain finite cumulative cycles/time and duplicate-launch refusal. Reviewer should choose bounded revise only for actionable in-scope repair; stop/partial for repeated identical failure, unavailable data, unresolved external wait after deadline, or exhausted budget. Never expand/reset budget silently.
6. **Docs:** clarify that task authorization covers ordinary reversible actions within its exact scope; it grants neither new scope nor external writes. Clarify technical failures do not by themselves trigger `wait_human`; terminal partial reports are not acceptance. Fix misleading “human decision needed” technical-exhaustion language.
7. **No change recommended:** identity/run/cycle/hash validation; fresh eval; human approval authenticity; no silent inventory/remote writes; no automatic recovery/replay; finite bounds; duplicate-launch refusal; stop at budget; not equating exit 0/native completion with acceptance. These safeguards worked as intended in important parts of the case.

## D. Target regression tests

1. **Scoped approval:** an approval-required criterion enters a human blocker; unrelated authorized criteria continue/review; dependent action cannot proceed until a real user response is supplied.
2. **Technical failure is technical:** HTTP401/selector/fixture/evaluator/schema failure without an actual missing user input cannot synthesize `needs_human` or `human_resolved`; reviewer may boundedly revise or stop with evidence.
3. **No fake resolution:** `continue/revise/complete` after `wait_human` rejected absent actual user reply; model-authored statement/flag alone cannot manufacture the reply. Existing hash/run/cycle checks still apply.
4. **Unavailable fixture safety:** criterion becomes `not_tested`/blocked; no inventory edit or fixture substitution; overall required acceptance remains non-pass.
5. **Approval reuse:** same approval for unchanged reviewed scope/state is not re-requested; changed state/action invalidates only when policy requires it.
6. **Repeated failure/budget:** identical failure with no progress terminates in honest partial/stop by finite budget; no new cycle, deadline, or run is auto-created.
7. **Audit vs product success:** valid, complete audit report may pass its report-schema checks while product task remains partial; neither evaluator nor reviewer marks product accepted unless every required criterion independently passes.
8. **Partial model compatibility:** legacy `continue/revise/complete/wait_human/stop`, config, run identity, receiver entries and existing clients retain semantics; new per-criterion schema is versioned and old payloads do not silently gain acceptance.

## E. Short proposed copy (not applied)

**Docs:** “Authorization for a task covers ordinary, reversible actions needed within its explicitly stated scope. Do not ask again for permission already given. Read-only authorization never permits writes. If one criterion needs a person, pause only dependent actions and continue other authorized work. Technical failures are not human blockers by themselves. Keep unknown and unavailable checks non-passing; report partial/stop when limits end.”

**Task generator:** “Carry forward explicit scope and prior decisions. Do not ask routine confirmation for in-scope files, tests, or reversible steps. Identify blockers by the action/criterion they affect; keep independent authorized work moving. Ask one concise, bundled question only for genuinely missing access, approval, input, or material choice. Never infer write scope from read access, invent approval, alter protected data, or reset limits.”
