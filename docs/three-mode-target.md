# PPP three-mode target architecture

**Status: native Goal, native Ralph and ping-pong boundaries are implemented with deterministic tests. Native Ralph snapshot/storage limitations remain explicit; no live-model compatibility/acceptance claim.** This design supersedes conflicting lifecycle and planning proposals in older architecture/roadmap documents. The [operational contract](../references/reviewed-runs.md) and [current protocol](action-scoped-protocol.md) describe today's interface until an explicit, compatible implementation and migration say otherwise. Current config validation also accepts `ping-pong`; its ordinary Pi Worker has per-iteration review and evidence-backed continuation. Goal now follows the native result boundary below, including full authorized action scope, post-result review and remaining-budget corrections in the same Pi history. Ralph now runs its own multi-iteration native loop over the full dispatched task and receives independent result review, preserving cumulative iteration/time bounds. See [native storage and feedback limitations](project-workspace.md).

## One run, three execution modes

The user chooses and plans the task and any separate runs. PPP does not automatically plan a campaign or require task decomposition. Each run has one shared Core and an independent Reviewer; execution adapters preserve the chosen runtime's own lifecycle rather than making three separate protocols.

| Mode | Target Worker lifecycle | Review boundary and continuation |
|---|---|---|
| Native Ralph | Native Ralph independently executes its bounded loop. | Independent Reviewer assesses its result after the loop; concrete corrections or unfinished authorized work remain within the run's cumulative budget. |
| Native Goal | Native Goal independently pursues its goal and completes through its native lifecycle. | Independent acceptance follows the result. Native completion is a lifecycle fact, not acceptance; corrections or remaining authorized work stay within the cumulative budget. |
| Ping-pong | An ordinary Pi Worker, not native Goal or Ralph, performs one logical iteration. | Reviewer assesses after each iteration. Core continues for unfinished authorized work or a concrete actionable defect, subject to budget and safe execution. Unknown review alone is not a defect or a reason to manufacture a correction. |

Worker runs ordinary relevant tests; Reviewer uses their actual results rather than duplicating deterministic checks and assesses remaining requirements and concrete defects independently. Core validates the run, evidence and review identity, chooses the next transition and preserves the distinction between result delivery and verified acceptance. There is no separate evaluator or task-specific evaluator repair loop. A negative review is actionable guidance, not a verdict to retry until positive.

## Shared boundaries

- Keep run/cycle and evidence identity, independent hash-bound review, ownership, durable delivery records and duplicate-launch refusal. No blind replay of attempted deliveries or uncertain external effects; reconcile what can be established and report uncertainty.
- Use finite cumulative run budgets, including corrections; do not silently reset or extend them. Account for native runtime and Reviewer limits accurately rather than infer unused allowance from missing telemetry.
- Use the selected project in place, including dirty changes; preserve unrelated user work. Scope and permissions come from actual task authority, not cwd or a successful test. Do not invent approval gates or require a clean checkout or separate worktree.
- Continue independent authorized work around real blockers and unavailable review. Deliver useful available results even when review is unknown, with exact unverified items and genuine human-dependent gaps grouped. Unknown is neither acceptance nor a synthetic defect; `finish` retains its existing verified-acceptance meaning unless explicitly and compatibly changed.
- Ask for human input only for an actual missing input, access, approval or material choice. Ordinary tests, native completion and a successful process exit cannot alone establish acceptance.

## Remaining implementation and validation

All three modes integrate their execution/review boundaries with shared Core, budgets, identity and delivery. Goal progress checkpoints and external operations no longer impose review waits; actual native completion/limitation is the boundary. Concrete corrections use only the remaining cumulative Worker tokens/time. Existing action/cycle IDs stay compatible, with additive dispatched `action_ids`; old sessions without that field remain single-action recovery scopes. Ralph reserves its finite native iteration window before launch; a matching normal terminal result releases unused reservations, while interruption/error/cancellation or missing telemetry retains the reserved bound. Concrete corrections launch only with the remaining cumulative allowance. Exclusive absent root-native storage, safely reused by the same run after confirmed ownership/cleanup, gives best-effort product feedback; private fallback preserves existing user/parallel native files and continues in-place work without claiming product snapshot visibility. In-project `.pi-ping-pong` noise and vendor snapshot bounds remain upstream limitations, not acceptance or dirty-project bans. Preserve existing CLI, config, receiver and run compatibility, or document and test any necessary migration. Existing native Ralph telemetry limitations are described in [project workspace](project-workspace.md).

Mixed native dispatches reserve all participating budget scopes without splitting the objective; Ralph windows use the smallest remaining participating allowance. Ralph token-bound cancellation and a standard-Node spawn/host-loss guard cover native RPC children and their tracked detached shell groups; Core checks live groups rather than trusting cleanup markers alone; unreconciled child ownership prevents unsafe review/replay. Further native telemetry isolation needs upstream support. Recovery must retain cumulative accounting and avoid blind replay, and report limits where safe reconciliation is unavailable. Validate with focused tests and appropriate integration/live evidence; tests and design text do not themselves prove live acceptance. Keep current operational instructions authoritative until implementation changes them.

Non-live fault tests exercise the real installed Pi bundled CLI and RPC bash, covering startup, host loss, iteration timeout, token stop, native-style SIGKILL and normal exit. Live-model task execution/acceptance remains unverified.
