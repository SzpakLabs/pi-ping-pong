# Product workspace and interrupted-output discovery

## Product placement

PPP uses the selected current project and its actual uncommitted state. A new product belongs at the requested repository root; an existing project is edited in place. An explicit subdirectory or file takes precedence. Preparation records that absolute path in `execution_contract.target` and TASK, together with project command cwd and actual allowed scope. No new project mode or config field is required.

No mandatory auto-commit, clean Git, fetch, separate worktree or routine approval. A selected existing non-Git folder is used directly, including without a UI; only an actually unavailable folder needs another target/private-store choice. Preserve unrelated staged/unstaged/untracked files and ignored local configuration. Do not copy secrets or create an alternative checkout merely because the project is dirty. Task authority remains the boundary; cwd and Git ancestry do not expand it.

`.pi-ping-pong/runs/<name>/work/` holds checkpoint, context, logs and service evidence, not the product by default. Explicit isolated test targets inside work/ remain supported. Goal/ping-pong Worker starts in an existing target directory, or the nearest existing parent for a file/missing target. Native Ralph starts its controller/children in private `ralph/<cycle>/` storage to isolate the vendor's cwd registry; its task gives the absolute product command cwd and directs edits/tests there. Product placement is still the recorded target, never a broader parent. Context and checkpoint paths are absolute and remain valid after `cd`.

Worker commands receive `PPP_WORK_DIR`, `PPP_CHECKPOINT_PATH`, `PPP_CONTEXT_PATH` and `PPP_TARGET` as exact values; `PPP_TARGET` may be descriptive, not a filesystem path. Evidence relative paths resolve from `PPP_WORK_DIR`. `PPP_CHECKPOINT_CMD` points to the optional `scripts/ppp_checkpoint.py` helper: it takes identity only from `cycle-context.json`, resolves bare target names and `work/`-prefixed paths, copies non-secret files from outside target/work (e.g. `/tmp`) into `work/evidence/`, writes atomically, runs Core's checkpoint validation and restores the previous checkpoint if rejected. These conveniences reduce transcription errors, but neither cwd nor environment variables sandbox Pi tools or shell commands. Ordinary temporary files outside the target are not universally a scope violation; respect any explicit TASK restrictions on where files may be written.

## Native Ralph task placement and limits (vendor 2.1.2)

Native Ralph snapshots `dirname(RALPH.md)`, not shell cwd, and writes fixed `.ralph-runner` artifacts both there and in its cwd registry. The CLI accepts a directory or a file named exactly `RALPH.md`; changing only the task filename or using a symlink does not isolate those artifacts.

PPP uses the real existing directory target for native feedback **when it can exclusively create both absent `RALPH.md` and `.ralph-runner`, or verify and reuse storage created by this same run**. Existing tasks, runners (including another PPP run), symlinks, unavailable storage, file/missing/descriptive targets and paths the native CLI cannot quote use private `ralph/<cycle>/RALPH.md` instead. A file target never scans its siblings as though they were authorized. This is storage fallback, not a refusal to work: the native loop still edits the authorized dirty project in place. The task and status record the chosen path and exact feedback limitation. Ralph's controller/children start in private storage so its cwd registry cannot overwrite an existing project runner; the task directs shell commands to the recorded product cwd.

Root service files are created exclusively, task mode 0600 and runner mode 0700; Pi and native children inherit umask 0077. Existing user files are never replaced, moved or deleted. Corrections can reuse this run's root storage only after a matching task hash, task/runner device+inode identities, terminal native token/path/cwd/bound and confirmed process cleanup. A nonblocking directory lease prevents concurrent PPP reuse; native Ralph also claims its active-loop registry. Before rewriting its own task, PPP retains the previous task and native result in that cycle's private `native-task.md` / `native-result.json`. Modified, replaced, foreign, leased or unreconciled storage falls back to private task storage without overwriting it. A different run never takes over retained root artifacts. These checks preserve parallel runs rather than requiring a clean or idle project. Preserve existing `RALPH_PROGRESS.md`; native may read it, but Worker is instructed not to overwrite it.

When PPP places native storage in a Git target, it hides its own `RALPH.md` and `.ralph-runner/` from the user's `git status` by appending root-anchored patterns to the repository's local `.git/info/exclude` (resolved via `git rev-parse --git-path`, so worktrees and nested targets work). This file is per-clone and never committed; tracked files and the user's `.gitignore` are not modified. Patterns are added once (repeat runs do not duplicate), only for paths that are neither tracked nor already ignored; a missing `.git/info/` is created as `git init` would. A non-Git target is skipped silently. Any Git or write failure records `ralph.storage_exclude_unavailable` and never blocks the run. Existing user `RALPH.md` files are never deleted, and the patterns stay after the run (removing them is a manual local edit).

Natural feedback is best-effort, **not clean product telemetry**. Vendor snapshots ignore `.ralph-runner`, but not `.pi-ping-pong` or secret/configuration filenames. Existing in-project PPP artifacts can consume the 200-file / 2-MiB bound, and service-only changes can count as progress; concurrent user edits are not Worker authorship. Private fallback snapshots do not observe product edits at all, so native progress may be false despite useful work. These facts are passed to Worker and retained in session/context/report evidence. Native progress, exhaustion, completion and exit 0 never establish acceptance or justify a synthetic correction. No extra evaluator or snapshot imitation is installed. Separately configurable native snapshot exclusions/scope and artifact storage require upstream support.

Ralph detaches its RPC children into separate process groups. PPP requests token-bound native cancellation and allows a bounded cleanup drain before stopping the host. A local Node preload (not a vendor patch) observes standard Node `ChildProcess.spawn`, not Pi's internal/bundled shell-module tracker. It records native child PIDs and their directly spawned detached groups, removes itself from project Node commands, and drains tracked shell groups on host loss, timeout, token-bound stop, ordinary exit or fatal error. Ralph's SIGKILL of a still-owned native child first becomes SIGTERM so its guard can drain, with a 250-ms SIGKILL fallback while that exact child remains owned. A `cleaned` marker records an attempted drain, not proof of cleanup: Core independently checks the native child and every recorded group for live non-zombie members, never signals a potentially reused PID, and prevents unsafe Worker/Reviewer overlap if cleanup cannot be reconciled. Existing results remain deliverable. Legacy markers lacking detached-group identities cannot confirm cleanup. Arbitrary descendants that deliberately create a new session from inside a project shell are outside this tracked-group guarantee; no general daemon cleanup or external-effect reconciliation is inferred. An unsupported host that does not initialize the guard cannot dispatch a native loop. Native iteration usage is reserved before launch (at most 50 per loop, the vendor 2.1.2 maximum; the original cumulative grant is unchanged); only a hash/identity-matched ordinary terminal result releases unused reservations. Interrupted/error/cancelled or missing telemetry retains the full reserved bound, never inferred spare allowance. Resume preserves old consumption and does not blindly restart a native loop.

## Launch baseline and fallback

Core attempts one private `output-baseline.json` before initial dispatch. It records absolute scoped paths and content hashes, not commits or Git index changes. The only source copy is the separate Git launch record below: the user's uncommitted `git diff HEAD` edits and untracked text, with the same private/size filters. Only work/ and the actual configured absolute target are considered; a file target does not authorize scanning its siblings. Non-Git projects work the same way. Existing dirty, untracked and ordinary ignored product files are compared by content, so a further edit can be detected even when Git status and mtime are unchanged.

Discovery is bounded to 4,000 entries, 32 MiB read, 1 MiB per file and three seconds per snapshot. Hidden/private/configuration paths, symlinks and dependency/cache directories are omitted; errors, concurrent changes and exhausted bounds are reported as partial visibility. These are fallback limits, not restrictions on task execution or explicit checkpoints. No secrets should be put in evidence; conservative filename/content filtering is not a general secret detector.

### Git launch record and start→current diff

When the absolute target is inside a Git repository with a HEAD commit, Core also writes one private `launch-git.json` before initial dispatch (never on resume): `git rev-parse HEAD`, a per-file `git diff HEAD` patch for files dirty at launch and the text of untracked files (`git ls-files -o --exclude-standard`), limited to the target path (a file target records only that file). It uses read-only Git commands with `GIT_OPTIONAL_LOCKS=0` and `core.fsmonitor=false`: no index refresh, `index.lock`, ref, object or history change. Hidden/private/configuration/dependency paths (the `output_snapshot.private_path` filter), binary, potentially secret-bearing, over-256-KiB files and anything beyond 200 recorded files, 4 MiB or 5 seconds are omitted and listed as unknown. A non-Git, HEAD-less or unavailable target simply has no record; a Git error, timeout or storage failure records `outputs.launch_git_unavailable` and the run continues.

Each Reviewer request then gets `reviews/v2-NNNNNN/launch-diff.txt`: a unified line diff from the launch state (recorded HEAD blob + launch patch, or recorded untracked text) to the current file for files that were dirty/untracked at launch and changed since. `request.json` binds it as `launch_diff.path`/`sha256` with `coverage` (`complete`, `partial` or `unknown`), per-file status (`unchanged`, `changed`, `deleted` or `unknown` with reason; `removed_lines` counts) and `truncated` (256 KiB diff ceiling); a later substitution is rejected like other evidence. Reviewer may cite it as `launch-diff`. It stays in the private review directory, not the evidence archive. It is a fact for the Reviewer, not a verdict or authorship proof: concurrent user edits are possible, and files clean at launch are not listed. A removed or rewritten user launch line that TASK does not justify is a concrete defect; missing/partial material stays unknown and never yields a synthetic correction.

There is no tree scan at every checkpoint. After a real interruption or Goal budget boundary without a usable checkpoint, Core compares a bounded current subset with launch hashes. It also retains safe exact write/edit references and shell facts from the matching owned session when available. Relative tool paths use that session's recorded initial cwd. Shell-created files can therefore be found without a write/edit reference. Fallback retention selects at most `max_evidence_files` candidate references (default 20), plus its manifest, prioritizing exact session references; other paths stay listed in the result manifest. Candidate text retention is bounded, hash-checked and best-effort; omitted binary, private, oversized, changing or unavailable files remain a stated limitation.

A candidate is **not proof of Worker authorship, test execution or acceptance**. It may include concurrent user edits or work from earlier cycles. Missing/mismatched baselines make origin unknown; partial snapshots cannot establish that a previously unobserved file is new. Unchanged baseline files are not swept into the result. Existing files are never restored, deleted or overwritten by discovery. Retained content is private, hash-bound evidence; ordinary tests and independent review still establish only their actual claims.

## Recovery and compatibility

The chosen initial Worker cwd is persisted with session state. Resume does not regenerate a purported pre-run baseline or silently change an old native session's cwd. Older runs without a recorded cwd retain their original work/ context. Descriptive/non-filesystem targets retain the compatible work/ cwd and work-only discovery.

Valid matching checkpoints are used on recovery; fallback discovery does not replace them. Native session/run/window identities, Goal cumulative usage/high-water, finite grants, ownership locks, delivery receipts and no-blind-replay rules remain. Internal snapshot/retention failures never become model preflight, automatic acceptance, permission to replay effects or a new human approval gate. Available results are delivered with exact limitations.

## Installed-runtime non-live coverage

The fault suite runs the configured installed Pi CLI (`PI_PACKAGE_JSON`, including its bundled entrypoint) in a private offline profile without model prompts or credentials. Real RPC `bash` creates a detached shell and nested Node process; host crash, timeout, token stop, native-style SIGKILL and normal RPC exit must leave no live members in the recorded shell groups. A separate regression rejects a forged-success `cleaned` marker while a recorded group is still alive. These checks establish startup and bounded local cleanup, not live-model/native task acceptance.
