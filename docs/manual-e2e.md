# Ручные E2E: три обычные задачи

**Новый цикл Worker → Reviewer → Core пока не имеет нового live-подтверждения.** Следующая процедура — путь нового запуска, а перечисленные прежние результаты относятся к удалённой evaluator-архитектуре. **История:** Кейс 1: попытка `test-e2e-basic-01` завершилась сбоем подготовки до Worker; после исправления следующая попытка `test-e2e-basic-02` завершилась с независимой приёмкой и Core finish. Кейс 2 и кейс 3: **NOT RUN**. Подробные приватные отчёты сохранены в `.pi-ping-pong/manual-e2e/test-e2e-basic-01/report.md` и `.pi-ping-pong/manual-e2e/test-e2e-basic-02/report.md`. Этот документ заменяет старые инструкции о pinned smoke-стенде; старые отчёты — история, не обязательный preflight.

## Как запускать

1. Открой обычный новый Pi-чат в выбранном worktree Pi Ping Pong с уже настроенной подпиской.
2. Вставь один из промптов ниже **обычным сообщением**, не slash-командой. Агент сначала сохраняет отчёт попытки, затем готовит TASK/config, но не запускает Worker.
3. Агент выдаёт точную `/ppp /absolute/path/config.json`. Выполни её сам в том же чате. Если команда не зарегистрирована, проверь `/` и обычную установку receiver; не запускай отдельный Pi ради обхода ошибки.
4. После запуска агент обрабатывает реальные сообщения протокола и обновляет отчёт. Каждый callback в чат запуска оформляется по формату **STATUS → TL;DR → Summary → Report → Suggested action → Full run status**: сперва суть задачи, затем короткий отчёт, после этого полный статус идентичностей/циклов/лимитов/критериев/блокеров и неизвестных. Пути — только подтверждающие ссылки, не замена сути. См. [обязательный формат callback](../references/reviewed-runs.md). Если сообщений нет, используй промпт диагностики в конце. Не перезапускай run ради получения красивого результата.
5. Для следующего кейса открой другой чат. Для новой попытки того же кейса явно выбери новый суффикс (`-02`), сохранив старую попытку.

Сценарии запускаются последовательно. Промпты разрешают подготовку; каждый live-запуск разрешает сам пользователь своей командой. Кейс 1 прошёл live-запуск attempt 02 на прежней evaluator-архитектуре; это не проверка нового цикла. Для нового basic запуска используй следующий свободный suffix, не переиспользуй существующие attempts; case 2 и case 3 live-запусков пока не имеют.

## Общий контракт для агента

- Работай в указанном worktree, используй его текущий код. Не создавай временный проект, clone, другой worktree, HOME, профиль OAuth, tmux, отдельный Reviewer TUI или копию runtime. Штатный Worker/Core, запускаемый продуктом, — часть теста, а не запрет на дочерние процессы.
- Используй установленный Pi и существующую ChatGPT-подписку (`openai-codex`). Не нужен фиксированный Pi 1.3.0, повторный OAuth или API-key fallback для моделей. Версии и обновления **записывай как наблюдения**, не сравнивай с историческим manifest и не откатывай. Ошибку реальной совместимости сохраняй как результат.
- Не запускай `prepare_goal_smoke.py` или `test_goal_profile.mjs`: они относятся к старому стенду. Не требуй прохождения их pinned-runtime проверок. Быстрый combined `bun run check` выполняется перед реальным запуском. Дополнительно запускай только относящиеся к изменениям медленные `bun run check:bridge` и/или `bun run check:faults` по правилам `AGENTS.md`; это не повод запускать старые profile probes или строить новую инфраструктуру.
- Проверь, откуда реально загружены receiver/bridge. Наличие исходника в worktree само по себе не переключает установленную копию. Обычная синхронизация через `python3 scripts/install.py` и `/reload` допустима при необходимости; объясни её пользователю, не загружай второй receiver. Не делай `PI_PING_PONG_BRIDGE` обязательным условием: это необязательный override, а не часть задания. Не меняй vendor, глобальные Goal/Ralph settings или auth.
- Все результаты держи в игнорируемой `.pi-ping-pong/` этого worktree. До подготовки создай `.pi-ping-pong/manual-e2e/<attempt>/report.md` по [шаблону](manual-e2e-report-template.md). Сначала сохрани исходный промпт и NOT RUN. При ошибке подготовки отчёт уже должен существовать.
- Run: `.pi-ping-pong/runs/<attempt>/`; файлы этих изолированных тестовых задач: `RUN/work/`. Это явно заданный scope трёх кейсов, не product default: обычный продукт создаётся в целевом проекте, а run/work хранит служебные файлы. Не перезаписывай существующую попытку. Файлы отчёта приватные; не добавляй их в Git. Если `.pi-ping-pong/` не игнорируется, исправь только проектный ignore с разрешения пользователя, не глобальный Git config.
- Подготовь только TASK.md и config.json, protocol 2 / schema 1, без eval.py, eval_argv или evaluator preflight. Каждый каталог .pi-ping-pong/, runs/, <attempt>/ — mode 0700; TASK/config — 0600. Worker выполняет обычные тесты, сохраняет команды, exit status, output и артефакты. Reviewer использует эти результаты без повторного доказательства deterministic checks и оценивает только оставшиеся вопросы/конкретные дефекты. Нет обязательного pre-work review или пре/пост повторов. Unknown не порождает фиктивный Worker cycle; существующая работа выдаётся честно как unverified при нехватке review.
- Worker не редактирует config/TASK/state/reviews. Для браузера сохрани общий Playwright route/cwd в TASK: Core передаёт PPP_PLAYWRIGHT_MODULE Worker в Goal и Ralph. Ошибка resolution — ограничение проверки, не разрешение управлять desktop и не автоматический launch gate.
- Mode Goal; Worker `openai-codex/gpt-6-luna`, thinking low. Для новых MVP runs используй `review_transport=pi`, `review_execution=headless` и явные `review_provider`/`review_model`: Core запускает отдельную Reviewer RPC-сессию, Chat A получает только пассивные отчёты и передаёт подтверждённый human input. Модель A не обязана совпадать с Reviewer. Запиши фактические модели/session identities из Worker sessions и `reviews/v2-*/reviewer.json`, не только намерения конфига. Отдельный пользовательский TUI не нужен.
- [Headless adapter](headless-reviewer.md) проверен локальными synthetic fixtures, но это не live acceptance. Старые evaluator-era runs не поддерживают resume новым runtime; их файлы не менять. Новые configs без `review_execution` используют launching-chat review. Не запускай старый chat-execution draft как доказательство нового MVP-разделения. Доступ из других чатов, закрытие A и catch-up остаются Post-MVP; не заявляй их проверенными.
- Не вводи искусственное read/write-only ограничение: код, тесты, локальный сервер и Playwright требуют обычных инструментов. Не строй sandbox. Scope остаётся явным: только файлы кейса и его отчёт, без commit/push/deploy и доступа к чужим проектам. Случайный выход за scope фиксируй как дефект, не скрывай.
- Сохраняй run/cycle/hash checks, независимый Reviewer и обычные тесты, delivery records, запрет duplicate launch и реальные human gates. Не правь Core или acceptance ради успешного теста. Не имитируй Worker обычным ответом в чате.
- Перед запуском запиши конфиг и фактические лимиты. Для basic: main 4; для сайтов: main 10. Например, для подходящей задачи можно использовать cycle 600 s, review 600 s, wall 900 s; выбирай конечные лимиты по сложности задачи и явным запросам пользователя, а не считай эти числа обязательными. `wall_seconds` — лимит активной операции, не всей жизни run. Closure — штатная protocol-2 authority, не старый запрет closure из двухциклового smoke. Эти числа не гарантия стоимости и не скрытое разрешение на новые main grants.
- Не читай credentials и не сохраняй их значения. Usage бери из доступных ответов/логов; отсутствующее отмечай unknown, не 0. Неизвестный usage не запрещает следующий ручной прогон автоматически. Каталожные USD оценки не называй расходами подписки.
- Отчёт обновляй после реальных checkpoints, проверок, human wait и терминального события. Не опрашивай моделью состояние в цикле. Native exit 0/Goal complete не равны acceptance. Если очередь молчит или чат закрыт, сырые run-файлы остаются; после возврата делай диагностику, а не новый запуск.

## Кейс 1 — функция и тесты

**Case 1 history:** `test-e2e-basic-01` — FAIL/INCOMPLETE до Worker (evaluator получал `PPP_EVAL_CONTEXT` как JSON-строку вместо пути к context file; storage `runs/` был не приватным). Общий evaluator helper/preflight и проверка private storage исправили preparation-path; `test-e2e-basic-02` прошёл одну Worker cycle, 23 независимые semantic checks, 9 unittest, review 1 и review 2, затем Core `execution=finish`, `status=complete`. Первая попытка остаётся неудачной; успешный отдельный повтор не переписывает её. Приватные подробности: `.pi-ping-pong/manual-e2e/test-e2e-basic-01/report.md` и `.pi-ping-pong/manual-e2e/test-e2e-basic-02/report.md`.

Для нового запуска case 1 нужен новый чат и следующий свободный attempt suffix; не переиспользуй ни `-01`, ни `-02`. Сам кейс проверяет базовый путь работы, проверки и завершения без браузера и внешних сервисов.

### Промпт в новый чат

```text
Работаем в текущем worktree Pi Ping Pong.
Прочитай docs/manual-e2e.md и выполни его общий контракт для кейса 1, attempt test-e2e-basic-03 (или следующий свободный suffix). Это подготовка реального Ping Pong Goal E2E, не выполнение задачи вместо Worker. Сначала создай приватный отчёт NOT RUN, затем подготовь TASK/config без отдельного evaluator. Дай одну точную /ppp-команду: я сам запущу её здесь. Без отдельного стенда, HOME и нового OAuth.

Задание Worker: в work/cart.py реализуй calculate_total(items, discount_percent=0, delivery=0). items — список пар (цена в целых копейках, целое количество). Цены и количество неотрицательные; discount_percent — целое от 0 до 100; delivery — неотрицательное целое. bool не считать целым входом. Неверные значения отклонять ValueError. Сначала сложить стоимость товаров, применить скидку ко всей сумме, округлить половину копейки вверх, затем добавить доставку. Для пустого списка итог 0, доставка не начисляется; аргументы всё равно валидировать. Пример: [(1000, 2), (500, 1)], скидка 10, доставка 300 => 2550. [(5, 1)], скидка 10 => 5. Только стандартная библиотека Python.
Добавь unittest в work/test_cart.py: обычная корзина, пустая, скидки 0/100, округление, отрицательные значения, неверные типы и bool. Запусти тесты. Worker сохраняет реальные результаты unittest; Reviewer использует их и проверяет только непокрытые требования или конкретные дефекты, не дублируя deterministic checks. Не меняй другие исходники репозитория. В отчёте сохраняй реальные события, проверки и итог, включая провал или отсутствие результата.
```

**Acceptance:** функция соответствует правилам; Worker tests проходят, Reviewer оценивает оставшиеся требования; реальный review и Core finish подтверждены файлами. Вопросы человеку по полностью заданной арифметике — лишняя эскалация. По отсутствующей технической возможности — конкретный дефект/блокер, не выдуманный PASS.

## Кейс 3 — сайт с реальной зависимостью от человека

**Attempt:** `test-e2e-human-01`. Это отдельный run, не переделка запущенного кейса 2. Проверяет полезную работу до блокера, ожидание и продолжение в том же run.

### Промпт в новый чат

```text
Работаем в текущем worktree Pi Ping Pong.
Прочитай docs/manual-e2e.md и выполни его общий контракт для кейса 3, attempt test-e2e-human-01. Сначала сохрани приватный отчёт NOT RUN, подготовь Ping Pong Goal run без отдельного evaluator. Задание Worker: сделай в work/site/ адаптивный одностраничник Test Studio: первый экран с CTA, три услуги, три тарифа, FAQ и доступная форма (имя, email, сообщение, согласие). Подготовь backend, обработку ошибок и конфигурацию PPP_TEST_RESEND_API_KEY, PPP_TEST_MAIL_FROM, PPP_TEST_MAIL_TO. Никаких ключей в браузере, исходниках, checkpoint, отчёте или чате. Для продолжения используй выбранный приложением приватный локальный config вне evidence (без вывода значений) либо документированный перезапуск только backend с новой env; не перезапускай Core/Worker run. Сохрани безопасный результат API (HTTP status/message id, без ключа и персональных данных); API acceptance не называй доказательством получения письма. Получение подтверждаю я или доступный delivery event. В отчёте отдельно оцени human wait, продолжение и реальную доставку. ### Что делает пользователь после запроса
```

- Можно **не предоставлять ничего**: сохраняем наблюдение quiet wait и BLOCKED; при завершении эксперимента пользователь отменяет run штатным способом.
- Можно предоставить данные локально способом, указанным приложением; в чат передать только факт готовности и разрешение на одну Test-отправку, без ключа. Агент выдаёт текущую `/ppp-respond <actual-run-id> <JSON>` с настоящими blocker IDs, не с примерами из документа. Пользователь подтверждает её в штатном UI.
- Сначала можно сообщить «готово», не добавляя конфигурацию: Reviewer должен оставить неподтверждённый блокер. Потом добавить действительную конфигурацию и повторить addressed response. Это необязательный отрицательный шаг, не разрешение имитировать валидацию.

**Раздельные результаты:**

1. Сайт и локальные проверки: PASS/FAIL/UNVERIFIED.
2. Human gate: PASS только если независимая работа сделана, отправка не подделана, запрос конкретен и ожидание не тратит Worker cycles (сравни сохранённые состояния с интервалом около минуты без model polling). Иначе UNVERIFIED/FAIL.
3. Продолжение: NOT RUN, пока пользователь не дал данные; PASS только при реальной валидации и продолжении с прежним run_id без нового запуска.
4. Доставка: NOT RUN/FAIL/UNVERIFIED/PASS по фактическим доказательствам. API 2xx без подтверждения получения — не delivery PASS.
5. Общая задача остаётся BLOCKED/INCOMPLETE, пока обязательная доставка не подтверждена. Не своди эти результаты к одному ложному PASS.

## Если запуск не состоялся, завис или отчёт не обновился

Вставь в исходный или новый чат; подставь attempt:

```text
В worktree этой попытки разберись с ручной E2E-попыткой <attempt> по docs/manual-e2e.md. Только диагностика и сохранение отчёта, без нового запуска, resume, resend review или повторной отправки email. Прочитай существующий report.md, run config/status/state, launcher.log, reviews, delivery records и необходимые части sessions. Не читай auth или секретный config приложения. Обнови отчёт: последнее доказанное событие, что не появилось, фактическая ошибка и какие проверки отсутствуют. Отсутствие файлов запиши буквально, не трактуй как успех. Не выводи «0 cycles/usage» без подтверждающих данных. Сохрани исходные логи; не чини Core и не удаляй попытку ради зелёного результата.
```

Если процесс оборвался до создания отчёта, восстанови отчёт из шаблона с пометкой «создан postmortem», временем обнаружения и неизвестным временем старта. Не выдавай восстановленный документ за contemporaneous log.

## Что меняем между прогонами

Не нужно замораживать установленный Pi или зависимости. Записывай обновления и исходную/конечную ревизию. Не меняй governing TASK/configuator уже запущенного run: это не старый лабораторный pin, а сохранение смысла конкретного эксперимента. Найденный дефект — отчёт; исправление и новый прогон — отдельная явно выбранная попытка.
