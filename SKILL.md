# Pi Ping Pong

## One task, one execution loop

Worker implements the user's task and runs ordinary tests. Independent Reviewer uses those results for what they establish and assesses only remaining requirement fit, visual/semantic judgment, omissions and concrete defects. Core validates identity, evidence, scope, dependencies, progress and budgets and independently chooses the transition. Chat A is the human command/report surface, not Reviewer or Core.

Do not generate or run task-specific `eval.py`, configure `eval_argv`, repair a separate evaluator or make a model re-prove deterministic tests. No mandatory pre-work model review or pre/post review repeat. Start authorized work from the recorded task contract. Review after an actual Worker result, or a concrete recovery/human/resource event requiring reconciliation. Unknown evidence alone must not manufacture another Worker iteration.

Continue all independent authorized actions around scoped blockers and unavailable review. Deliver existing work with exact unverified items and one grouped list of genuine human-dependent gaps. Delivery is not verified acceptance; a stop with only unverified criteria and no defect is reported as `delivered_unverified` ("delivered, not verified"). `finish` still requires all criteria passing, completed actions, resolved blockers and reconciled external effects; native completion/exit 0 is not acceptance. Do not reset budgets, replay ambiguous effects or infer authorization from a successful test. See [AGENTS.md](AGENTS.md).

## Prepare and launch

Read [the operational contract](references/reviewed-runs.md) and [protocol/schema](docs/action-scoped-protocol.md). Prepare private `TASK.md` and `config.json`, not the product. Use explicit protocol 2/schema 1. New Pi preparation uses `review_transport=pi`, `review_execution=headless` and explicit independent Reviewer provider/model. Omitted/chat execution retains the launching-chat review transport for new configs, not evaluator-era resume.

`/pi-ping-pong <task description>` reserves a private named run and sends the preparation prompt; a lone kebab-case argument selects that name. Defaults: Worker `openai-codex/gpt-6-luna`, low thinking, 10 cycles unless requested otherwise. Ask only for genuinely missing scope/input/choice. `/pi-ping-pong <ready-name>` or an actual config path explicitly launches. Menu selection alone does not launch; launch records forbid duplicates. Never prefill `pi_session_id` or mutate transcripts. The receiver binds the real launching session.

For browser work choose Playwright, not desktop control. Prefer configured/project-installed Node runtime; record route and cwd in TASK. Core resolves once and passes `PPP_PLAYWRIGHT_MODULE` to Worker for ordinary tests in both Goal and Ralph. Module resolution is not browser/login verification; failures do not block independent work. Reuse intended authenticated automation context; do not copy personal cookies or bypass security.

New run files: `.pi/ping-pong/runs/<name>/` in the existing worktree; PPP directories mode 0700, TASK/config mode 0600. Existing `.pi/` permissions are not changed. Legacy `.pi-ping-pong/runs/` stays discoverable in place; use the menu or exact config path when names collide. PPP tries a local Git exclude only for its new service path and warns without blocking if Git protection is absent or unknown. See [private run storage](docs/project-workspace.md#private-run-storage). Use the selected current project, including its uncommitted state: new products go in the requested repository root, existing projects are edited in place, and explicit subdirectory/file targets take precedence. Record the absolute product target in config/TASK. No mandatory auto-commit, clean Git, fetch, separate worktree or routine approval. Preserve unrelated user files and ignored local configuration. Explicitly authorized project source paths may be edited directly; `work/` is checkpoint/evidence storage, not a source checkout. Cwd/Git ancestry grants no write scope. Never store secrets in evidence. Simulated people's names contain Test.

Core records a best-effort bounded hash baseline before initial work and, for Git targets, a read-only launch record (HEAD plus filtered `git diff HEAD`/untracked text of the user's launch edits) that gives each Reviewer request a hash-bound start→current `launch-diff.txt` fact, not a verdict; only a no-checkpoint interruption/budget boundary triggers fallback discovery in work/ and the configured absolute target. Candidates include possible user/concurrent changes, not established Worker authorship, tests or acceptance. Missing/partial snapshots never gate work/delivery. See [project placement and fallback limits](docs/project-workspace.md).

For user-operated E2E follow [three manual cases](docs/manual-e2e.md): create the private report **before** preparation, use installed Pi/subscription and the existing worktree. Give the exact native launch command; if awaiting user entry, report **NOT RUN**, not failure. No new live/paid run without authorization. Historical pinned runtime/HOME/profile smoke requirements are not launch prerequisites.

## Work, review, recovery

`ping-pong` uses an ordinary Pi RPC Worker and reviews each settled iteration, charging task iterations to the cumulative cycle budget. Ping-pong checkpoint format/schema/identity repairs (`worker.checkpoint_invalid` → same reserved action/cycle redispatch; a missing/wrong `run_id`/cycle/action is never accepted, but is repaired or reviewed as unverified output, not halted) do not spend `max_cycles`; they have their own bound `checkpoint_repair_attempts` (optional config, default 3 per reserved action/cycle; 0 disables repair) and still spend cumulative `wall_seconds`. Used repairs are recorded as `checkpoint_repairs` on the consumption row and in `bridge-status.json`, separate from `worker_iterations`. At the limit Core records `worker.repair_budget_exhausted`, retains scoped outputs as an unverified result for independent review, and grants no new budget, replay or acceptance. Reviewer can identify specific remaining authorized work or a concrete correction with the optional evidence-backed `continuation` judgment, without inventing an experiment; unknown alone never qualifies. Goal autonomously pursues the full authorized objective through native continuation until native completion or a real limitation; progress checkpoints and external operations do not force review or `goal_wait`. Core freezes Worker before independent result review. Native completion is not acceptance; concrete corrections use the same Pi history (pointing only at changed cycle context, not rereading delivered CONTRACT/TASK) and only remaining cumulative time, launches and (if configured) tokens, with hash-bound review and no uncertain-effect replay. `goal_max_launches` (default 10) bounds new native Goal windows per run; `goal_tokens` is optional — set, it is a cumulative cap passed as native `--tokens`; unset, Goal runs without a token cap, bounded by `wall_seconds` and launches. Goal checkpoints do not spend `max_cycles`; `cycle_seconds` does not split native Goal work, and both fields are optional in Goal configs (required for Ralph and ping-pong). Ralph independently runs a bounded native multi-iteration loop over the full dispatched task, then receives result review; corrections/remaining work use only remaining cumulative native iterations/time. Iterations are reserved before launch; interruption or missing telemetry never implies spare allowance. Root-native task storage is created exclusively when absent and reused for corrections only after this run's hash/inode/native-token ownership and cleanup are confirmed; otherwise private fallback preserves existing files while work continues in place. Mixed native dispatches reserve every participating budget scope, without splitting the objective. Native snapshot feedback remains limited, especially with in-project PPP artifacts; see [placement/ownership limits](docs/project-workspace.md). Reviewer time has its separate finite `review_seconds`; response-format repairs reuse that same session/deadline, never a new task evaluation or Worker replay. Do not repeat valid negative findings to obtain a pass.

Worker checkpoints retain ordinary test commands, exit status, output and relevant source/artifacts. Optional `python3 "$PPP_CHECKPOINT_CMD" --status ... --summary ... EVIDENCE...` (`scripts/ppp_checkpoint.py`) fills identity from cycle-context, resolves evidence paths, copies non-secret files from outside target/work into `work/evidence/`, writes atomically and runs Core's checkpoint check; manual writing stays valid. Reviewer submits the existing action/criterion judgments through `assessment`; Core binds run/cycle/review/state/request/evidence hashes. `endorse` is not acceptance. Further Worker corrections need concrete defects or unfinished authorized work and a justified materially different next action, not unknown checks. Unavailable or incomplete review leaves acceptance unknown while independent actions and result delivery continue.

`resume`/event-driven `wake` preserve ownership, history, grants and accounting. Uncertain operations require independent reconciliation, never blind replay. Durable attempted reviews/delivery receipts forbid blind redispatch. Old evaluator-era configs and protocol 1 cannot launch/resume with this implementation; do not alter their files or silently migrate them. Git history contains their runtime.

Human responses use `/ppp-respond` (ordinary addressed text plus native confirmation), advanced run-ID JSON, or interactive `bridge.py human --config ...` for console transport. Ask only actual missing input/access/approval/material choice. Waiting/reminders use no Worker/model polling; late input never restarts terminal work.

## Reports and receiver

Use standalone `STATUS — ...`, then separate headings `### TL;DR`, `### Summary`, `### Report`, `### Suggested action`, `### Full run status`, with blank lines and content below. Explain completed versus accepted/unverified results, concrete errors, grouped real human needs and whether a stage actually started. Use available facts; no extra artifact reads just to fill status.

Chat A narrates Core reports without submitting decisions, changing state, extending budgets or starting workers. Core emits passive actual Worker/Reviewer start notices and deduplicates unchanged waits. Durable delivery is not acceptance. See [headless adapter](docs/headless-reviewer.md).

`/ppp` and `/reviewed-run` alias the launcher; `/ppp-status` and `/reviewed-status` alias read-only local status. Receiver attachments/session entries and message envelopes stay compatible; existing runs remain inspectable without execution. Delivery uses Pi's existing `sendMessage` follow-up API, not session-file writes or desktop automation. Codex queue targets the exact existing thread; do not start a second writer via `codex exec resume`.

Checks are listed in AGENTS.md. Unit/fake-process results do not establish live model acceptance or UI-close autonomy. No commit, push, deploy, global runtime install or settings changes unless authorized.
