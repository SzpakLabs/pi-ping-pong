# Reviewed run setup

## Current lifecycle and compatibility

Worker executes and runs ordinary tests; independent Reviewer assesses only what those tests cannot establish and concrete defects; Core validates and chooses transitions. There is no separate evaluator, generated eval.py, evaluator repair loop or mandatory pre-work model review. Never re-prove deterministic checks with a model solely for another verdict. Unknown verification does not imply a product defect or another Worker iteration.

Current configs use **protocol 2 / schema 1**, without `eval_argv`. `mode=ping-pong` selects an ordinary Pi RPC Worker, with review after each settled iteration and the existing cumulative cycle budget. An independent Reviewer may continue the selected eligible action with a specific evidence-backed `continuation` identifying remaining authorized work or a concrete correction; no experiment is required. Unknown review alone is not a continuation. Goal now pursues the full authorized objective through native continuation and is reviewed after native completion or a real limitation. Ralph independently runs a bounded native multi-iteration loop over the full dispatched task; Reviewer assesses after its result/real limitation. Corrections and remaining authorized work use only remaining cumulative native iterations/time, not a renewed per-review budget. The action/criterion assessment schema and receiver session/message identities remain; Reviewer now submits judgments directly through `assessment`. `review-v2 --assessment` replaces evaluator endorsement/correction. `correct`, `--correction`, `--human-needs`, legacy `decide` semantics, protocol 1 and evaluator-era resume are not supported. Existing old run files are preserved, not migrated; use Git history to recover their original runtime. Existing receiver status/attachments and launcher aliases remain compatible. An old config is rejected before binding a session or creating a launch record.

Continue every independent authorized action despite a scoped blocker or failed review. Deliver existing work, explicitly unverified where necessary, and group genuinely human-dependent gaps. Only actual missing input/access/approval/choice warrants escalation; internal role/schema failures do not. `finish` is verified acceptance, not merely delivery. Preserve finite cumulative budgets, immutable evidence, protected identity, ownership, no uncertain-effect replay and no false acceptance.

## Preparation

Create only private `TASK.md` and `config.json` in the reserved run directory. Product work defaults to the selected current project with its current uncommitted files: new project at the requested repository root, existing project in place, explicit subdirectory/file respected. Record absolute product target and project command cwd; no mandatory clean Git, commit, fetch, separate worktree or routine approval. Preserve unrelated user work and ignored local configuration. No `eval.py` or evaluator preflight. TASK records actual requirements, allowed paths and ordinary test commands where known. Worker retains test commands, exits, output and relevant artifacts with its checkpoint. When practical, save stdout/stderr and the actual exit in the same ordinary shell command, with the checkpoint in that call; this is a recommendation, not an extra runner/test gate. An interrupted command's exit remains unknown. Scope comes from the task, not cwd or Git ancestry. Files in an absolute authorized filesystem target may be checkpoint evidence directly; `work/` remains evidence storage, not a source checkout.

  "run_id": "b739c07d-9af8-41a7-80fa-496e3b7c9f20",

Optional `worker_extensions` and `reviewer_extensions` are lists of Pi extension paths, for example `"worker_extensions": ["/absolute/path/to/provider/src/index.ts"], "reviewer_extensions": ["/absolute/path/to/reviewer-provider/src/index.ts"]`. Relative paths resolve against the config directory. Worker paths are passed only to Worker Pi; Reviewer paths only to the separate headless Reviewer Pi (not chat review). Pi still starts with `--no-extensions`; only explicitly configured paths and the existing native Goal/Ralph extension load. Extensions execute code with the respective process's privileges: configure only trusted extensions. Native Ralph's installed runner propagates parent extensions to iteration subprocesses when the selected model is registered by an extension; it does not propagate them for built-in models. Provider registration and credentials remain the user's existing Pi configuration; these fields do not install extensions or modify global settings.

New named runs live in `.pi/ping-pong/runs/<name>/`; existing `.pi-ping-pong/runs/` stays readable in place. PPP-owned directories use mode 0700, TASK/config mode 0600. Do not chmod existing Pi settings directories. A local Git exclude for `/.pi/ping-pong/` is best effort: an absent or unknown ignore is a warning, not a gate. See [private run storage](../docs/project-workspace.md#private-run-storage). Use a unique UUID for named-run run_id, never a fake `pi_session_id`; explicit launch binds the actual session. Never copy secrets. Default preparation Worker is openai-codex/gpt-6-luna, low, 10 cycles unless requested otherwise. Current Pi model is the Reviewer preparation default, not a headless launch model requirement. `review_execution=chat`/omitted retains the launching-chat path for **new evaluator-free configs**. Codex transport needs the exact existing thread_id; no second desktop writer.

For browser work use Playwright. Core resolves configured/project-installed Node module once and passes `PPP_PLAYWRIGHT_MODULE` to Worker for ordinary tests in both modes. Record route/cwd in TASK. Module resolution is not browser binary/auth verification; continue independent work if unavailable. Preserve authenticated automation-session boundaries and actual external authorization.

## Launch and checkpoints

Use `/pi-ping-pong <ready-name>` or `/pi-ping-pong /absolute/run/config.json` in the intended existing Pi chat. `/ppp` and `/reviewed-run` are aliases. For same-name runs in both locations, choose the intended menu row or explicit config path. Preparation/menu selection never launches. Config launch records forbid duplicate starts. `/ppp-status` is local read-only inspection, not a model/evaluator call. Receiver subscriptions persist as existing `pi-reviewed-run` entries; reopening the same session restores monitoring, not a new launch. Do not edit transcripts.

For console/Codex execution:

```sh
python3 scripts/bridge.py run --config /absolute/run/config.json
```

Goal/ping-pong Worker cwd starts at the existing absolute target directory (or the nearest existing parent for a file/missing target); this cwd is persisted for native session recovery. Ralph controller/children start in private `ralph/<cycle>/` storage to avoid overwriting the vendor's cwd registry, with an explicit absolute product command cwd in the native task. Old runs with sessions keep their original work/ cwd. Service context and checkpoint paths are always absolute, regardless of shell cwd. Descriptive non-filesystem targets keep the compatible work/ cwd.

Worker writes `work/checkpoint.json` with protocol_version=2, schema_version=1, run_id, cycle, action_id, status=progress|ready|needs_human, summary, evidence, next_step and reason_code for a genuine human need. For Goal, `cycle-context.action_ids` holds the full authorized dispatch, including dependent work whose prerequisites are also dispatched; real blockers and their dependent actions stay excluded. `action_id` anchors compatible checkpoint/accounting identity, not a stopping boundary. Respect actual dependencies and operation IDs; ordinary progress checkpoints never force review or `goal_wait`. Ready/exit0/native completion is a claim, not acceptance. Evidence includes ordinary test logs and relevant source/artifacts; `max_evidence_files` defaults to 20 and bounds references, not artifact count. Use a compact manifest where useful; do not delete raw evidence to fit it. Worker may use the optional `"$PPP_CHECKPOINT_CMD"` helper (`scripts/ppp_checkpoint.py`) to fill identity from cycle-context, resolve or copy evidence and run Core's same checkpoint check; it adds no gate and manual checkpoints remain valid.

Fresh initial eligibility comes from the recorded authorized action/dependency graph, without a paid preflight. Reviewer runs after actual Worker results, or a concrete recovery/resolution/resource event. Core retains immutable evidence and validates state/request/checkpoint/live-and-retained hashes before recording/applying judgments. TASK text and current contract/checkpoint are delivered inline; retained test results and other material remain accessible through the read tool. Reviewer judges residual task questions, not transport ceremony. Missing read events alone create no gate; observed failed access to cited pass material leaves work unverified, without forced repeats. See [direct review schema](../docs/action-scoped-protocol.md).

## Budgets and Goal accounting

Goal checkpoints do not spend `max_cycles`; one Pi session/history persists across native results, corrections, token-window renewals and restoration, bounded by cumulative `wall_seconds` and `goal_max_launches` (optional integer >=1, default 10), plus an optional cumulative `goal_tokens` cap. A launch is a new native Goal window (new native Goal ID); RPC restarts, continuation of the same active/waiting Goal, checkpoints and corrections inside it, and recovery of the same window spend none. The window is reserved durably with its session row before dispatch, so recovery never charges it twice. When launches (or a configured token cap) are exhausted Core pauses for an explicit grant (`paused_budget`) and delivers available results without acceptance or automatic extension; a main grant of N adds N launches (and N × `goal_tokens` when configured). Without `goal_tokens`, `/goal` is started without `--tokens` (no per-window token cap); usage is still recorded as a high-water lower bound and unknown usage still blocks new Worker allowance. With `goal_tokens`, it keeps its cumulative meaning and the remaining total is passed as native `--tokens`. Native Goal runs until `goal_complete` or an actual stopped/waiting/budget boundary, not one external action or logical step. Core stops its owned RPC process before independent review, including a native wait that may own a timer; restoration retains the Pi history. Native completion never sets acceptance or requires a post-acceptance Worker turn. A correction prompt in the existing Pi session points Worker only at `work/cycle-context.json` (budget, feedback, next step) and does not demand rereading CONTRACT.md/TASK already in its context; a fresh `/goal` start still reads CONTRACT.md, TASK and cycle context. Concrete Reviewer corrections or unfinished authorized work can start a new native Goal after completion/stopping, with a fresh native ID but only the remaining cumulative allowance. An active externally waiting Goal retains its native window/ID on continuation. An explicit main grant of N cycles adds N configured token windows; after a spent window, the same Pi session starts another native Goal with only the remaining granted allowance. Each window is bound to the native Goal ID; recovery does not count the previous native Goal as new-window usage, and a persisted but undispatched window is retried after reconciliation. Native `budget_limited` is a normal boundary even when Goal aborts the turn before writing a checkpoint: Core saves reported token usage, independently reviews available outputs, and does not infer acceptance from the boundary or missing checkpoint. Resume preserves those grants before removing legacy checkpoint caps. Cumulative usage never resets. The bridge tracks observed cumulative Goal tokens, including repeated context and cache reads as reported by native Goal; this is not a dollar cap. Native accounting checks the limit at response boundaries, so the last response can exceed the configured token allowance. On an interrupted Worker, Core stops its owned Pi process and imports persisted native Goal snapshots from that exact Pi session/window; resume reconciles them before independent review or Core transitions. Imports use a per-window high-water mark, never reset grants/time or double-charge repeated recovery, and do not depend on an expired RPC deadline. Missing, foreign or incomplete native telemetry leaves recorded usage as a lower bound and remaining tokens explicitly unknown; independent verification/result delivery can continue, but no new Worker allowance is inferred from missing usage. When a reviewed correction or explicit grant replaces a stopped window, the bridge confirms Pi Goal's replacement dialog only after matching the prior native Goal ID and recorded stopped state (`budget_limited`, `blocked`, `paused` or `usage_limited`). A completed Goal needs no replacement confirmation in native Pi Goal. Unexpected dialogs fail visibly; no new user approval requirement is added. The Worker-start notice follows an actual Pi agent-start event. Choose a budget accordingly; never truncate recorded usage. Do not enable managed-run RPC globally: direct `/goal` and Pi's documented RPC transport suffice.


Native Goal uses cumulative active Worker `wall_seconds` and tokens; `max_cycles` and `cycle_seconds` are optional for Goal (still validated when present, still required for Ralph and ping-pong) and do not interrupt Goal per action/turn. At actual Worker time exhaustion, Core stops the process, reconciles owned native usage and independently reviews retained results; it does not launch another Worker after time is spent. Missing/malformed non-identity Goal checkpoints go through available-output discovery and result review, not a synthetic product replay just to repair metadata; Core's rejection diagnosis is carried into the next native Goal/Ralph dispatch's feedback and `cycle-context.json` `checkpoint_rejected`, without a new cycle or action replay. Worker wall/token/Ralph-iteration budgets exclude independent Reviewer time. Reviewer startup, response and same-session format repairs share finite review_seconds at that boundary; no reset or mandatory second review. Native usage unavailable means unknown/lower-bound, never zero or permission for more Worker tokens. Native `goal_complete` persists `complete` then clears goal-state; this applies to every window in the same session. Assistant turns after the completion (outside native `tokensUsed`) are added to the window's usage when each carries metered `usage.totalTokens`; any unmetered late turn leaves usage unknown. Outside Goal, token figures are report-only and never affect budgets. Ping-pong sums assistant `usage` (`totalTokens`, plus input/output/cacheRead/cacheWrite per session row) from each owned Worker session file at session end; the sum is recomputed from the whole file and keyed by session id, so recovery/repair never double counts. `bridge-status.json` reports `worker_tokens` with `worker_tokens_status` `known`, `partial` (torn lines or assistant turns without usage: lower bound) or `not_measured` (`null`, never 0). Native Ralph 2.1.2 runs iterations with `--no-session` and exposes no usage, so Ralph reports `worker_tokens: null`, `worker_tokens_status: not_measured` and `worker_tokens_reason`. Headless Reviewer sessions are summed the same way into `reviewer.json` and reported as `reviewer_tokens`/`reviewer_tokens_status`. Human waiting/reminders consume no Worker turns. Ping-pong checkpoint format/schema repairs (`worker.checkpoint_invalid` → same reserved action/cycle redispatch) do not spend `max_cycles`; they have their own bound `checkpoint_repair_attempts` (optional config, default 3 per reserved action/cycle; 0 disables repair) and still spend cumulative `wall_seconds`. Used repairs are recorded as `checkpoint_repairs` on the consumption row and in `bridge-status.json`, separate from `worker_iterations`. At the limit Core records `worker.repair_budget_exhausted`, retains scoped outputs as an unverified result for independent review, and grants no new budget, replay or acceptance.

## Native Ralph accounting and storage

`max_cycles` bounds cumulative native iterations, including corrections; one Core cycle may contain multiple native iterations and one post-loop review. `cycle_seconds` bounds each native iteration and `wall_seconds` bounds cumulative Worker time, separate from Reviewer time. Mixed native dispatches charge one reservation per participating scope for each native iteration, regardless of the checkpoint anchor. Ralph bounds its window by the smallest participating remaining scope and releases unused reservations in every scope; independent actions with remaining allowance can continue after review. Goal retains one shared cumulative token/time budget across scopes, not duplicated token windows. The additive `worker_scope_grants` ledger preserves existing single-scope ledger fields and legacy records. Core reserves the available finite iteration window before dispatch, capped at the vendor 2.1.2 limit of 50 per loop without changing the cumulative grant. Only a matching task hash/path/cwd/native token/bound and ordinary native terminal result releases unused reservations. Interrupted/error/cancelled or missing telemetry conservatively retains the full reservation. Resume never resets grants or blindly restarts the loop. Invalid non-identity checkpoints use available-result review, not metadata-only Worker replay. A checkpoint with a missing or wrong run/cycle/action identity is never accepted or archived as the Worker checkpoint, but it is a Worker checkpoint error, not a safety halt: ping-pong uses bounded checkpoint repair (the repair prompt names the expected identity), native Goal/Ralph carry the diagnosis forward and review available outputs as unverified.

Existing directory targets get natural native snapshots when absent `RALPH.md` and `.ralph-runner` can be created exclusively, or when this run's retained storage is safely verified for reuse. Existing/user/parallel native files are preserved; private fallback still executes the authorized dirty project in place. Root service artifacts remain retained; corrections reuse them only after hash/inode/native-token ownership, terminal result and process cleanup checks, preserving prior task/result archives. Foreign, modified or leased storage uses private fallback. Native snapshots include in-project PPP service noise from both stores and have strict coverage limits; private snapshots do not see product edits. Never infer product progress/acceptance from native telemetry. Token-bound cancellation and a standard-Node spawn guard cover native RPC children and their tracked detached shell groups; Core checks actual live groups independently of cleanup markers; uncertain child ownership prevents unsafe review/replay, not a fabricated approval request. See [exact storage, recovery and feedback limits](../docs/project-workspace.md).

## Human responses, delivery and recovery

Use `/ppp-respond`: choose the attached run and addressed question, supply ordinary non-secret text and confirm the constructed instruction. A Goal budget request offers 1 or 3 additional Goal launches or any whole number >=1; with configured `goal_tokens` each launch also adds `goal_tokens` and the confirmation shows the cumulative token limit, otherwise no token amount is shown. Advanced `/ppp-respond <run-id> <JSON>` remains. Console transport uses interactive `bridge.py human --config ...`; model/pipe flags do not grant approval. Authentic grants are additive/single-use; technical success cannot fabricate approval or a choice.

Continue independent work before one grouped human request. An unavailable/invalid Reviewer preserves current work under unverified-results/ and permits only independently eligible actions unaffected by the missing assessment or uncertain operations. Already identified genuine blockers are still grouped/delivered alongside the unverified result; review failure adds no human gate. No-checkpoint interruptions and Goal budget boundaries retain safe exact write/edit references and owned-session shell facts where available, plus unattributed file candidates from a bounded launch-hash comparison in work/ and the configured absolute filesystem target. The hash-only baseline is attempted once before initial work, never reconstructed as a pre-run baseline on resume; there is no per-cycle tree scan. For Git targets a read-only launch record (HEAD, filtered `git diff HEAD` patch, untracked text) lets each review request bind a start→current `launch-diff.txt` fact for launch-dirty files; it is not authorship or a verdict, and missing coverage stays unknown. Missing/partial snapshots do not block work/delivery, and candidates can include user/concurrent changes. No authorship, tests or acceptance is inferred. Prompts, read results and write/edit content are not copied from the transcript; known secret-bearing shell material is omitted. Hidden/private/configuration paths, symlinks, dependency/cache trees, binary/unbounded evidence and oversized files may remain undiscovered or unretained. Limits and uncertainty accompany delivery; see [workspace/discovery details](../docs/project-workspace.md). A durable unverified-results record and reports list actual available files/archive paths even after a valid unknown review or the first Reviewer failure. Missing process results/numeric exits are never inferred from tool success or test output. Delivery is not acceptance; the existing explicit token-grant pause remains. No synthetic correction from unknown; no fresh Reviewer merely to repeat a missing verdict. Missing checks remain unknown and are delivered honestly. When an applied review finds no defect, every action is complete and no uncertain operation, open blocker, wait or fail/blocked criterion remains, a stop with only unknown/not_tested criteria is recorded as `delivered_unverified` ("delivered, not verified"): not acceptance, no `finish`, no budget reset.

Explicit `resume`/event-driven `wake` retain task identity, grants, history and cumulative usage. Refuse duplicate controllers, live inherited leases, uncertain external replay and attempted reviews lacking durable disposition. An old callback file is not authorization or acceptance. Do not reset blocked review or redispatch ambiguous deliveries. Terminal runs cannot restart. Durable notices/receipts remain even if reporting fails; failed report delivery does not erase accepted work.

### Human-facing report formatting

Preparation reports and Chat A checkpoint/final/error reports start with a standalone `STATUS — <state and short explanation>` line. Follow with these exact Markdown headings, each on its own line with a blank line before and after: `### TL;DR`, `### Summary`, `### Report`, `### Suggested action`, `### Full run status`. Put content below headings, not beside inline bold labels. Use short paragraphs or bullets; put any command in a fenced `text` block. Keep Full run status compact and use only already available facts; do not read extra artifacts just to fill it or invent missing values. Passive Core stage notices remain short and do not need this section layout.

Checkpoint reports and automatic Core notices must be compact: run/check/cycle, ordinary test evidence and Reviewer outcomes, criteria, a short Worker checkpoint claim when present, actual errors or necessary human input, and what happens next. Chat A must turn queued reporter requests into visible STATUS/TL;DR/Summary/Report/Suggested action sections, not merely display artifacts or acknowledge receipt. Core stage notices stay compact; full JSON stays in artifacts. Start with current bridge-status and the compact Core facts in the reporter request. Healthy matching terminal results require no further artifact reads. On a material mismatch, read current execution-state once, then only the applied review or one measurement as necessary; full source/logs require concrete diagnosis. Distinguish historical checkpoints from current state. Explicitly state whether a reply is required, exactly which input/choice and why, or no reply needed. Internal verification retry/blockage is not a human-response request; do not imply /ppp-respond can repair missing review evidence. Preserve lifecycle versus acceptance: endorsement or exit 0 is not completion. Narrate after Core selects its transition: emit one terminal report, not both a pre-transition review report and a terminal report. A selected action is not an actual Worker start. Pending state reports may be coalesced by the receiver with durable supersession receipts; addressed human questions are never coalesced. Do not repeat a current terminal outcome already reported in the conversation. Emit separate passive notifications after successful Worker startup, validated Headless Reviewer startup. If no stage starts, explicitly state terminal completion/stop or the recorded waiting source; deduplicate unchanged waits. A blocked verification/error must say no new stage started and why. Ask only for actual missing input/access/approval/choice, never routine confirmation. Detailed protocol state, identities, grants, usage and evidence remain in private artifacts; link `/ppp-status` for the current local view. These are reporting changes, not new Core authority or replay permission.
